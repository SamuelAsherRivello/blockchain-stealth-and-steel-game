# ArkadeOS features and what BIS demonstrates

Reviewed 2026-10-08 against the adjacent `blockchain-integration-service` checkout, this game's BIS host, and the current Arkade documentation. **“Demonstrates” means BIS has a user facing or game facing implementation; it does not imply production readiness or live acceptance of every path.** Arkade capabilities also depend on the selected operator, network, SDK version, and any additional provider. BIS currently targets Signet and Mutinynet test networks; its game uses a pinned local BIS package snapshot.

Here, *roles* means the ten main jobs Arkade can perform for an application. These are a useful product map, not Arkade's official ten part taxonomy.

| # | Arkade role and function | BIS demonstration | Gap or next game idea |
| --- | --- | --- | --- |
| 1 | **Wallet identity and custody.** Create or restore a wallet, derive addresses, and sign as the owner. [Arkade wallet setup](https://docs.arkadeos.com/wallets/getting-started/create-your-wallet) | **Yes.** Player and game wallets use mnemonic identities; BIS saves account access in origin scoped encrypted browser storage and restores it. | Offer an external signer or device bound approval option for a game treasury. A wallet in the browser is convenient, but a second device could hold the key for high value actions. |
| 2 | **Offchain BTC payments.** Receive at an Arkade address and send BTC to another Arkade wallet, including an offline recipient. [Receive](https://docs.arkadeos.com/wallets/operations/receiving-payments), [send](https://docs.arkadeos.com/wallets/operations/sending-payments) | **Yes, with limits.** BIS shows an address and provides reviewed direct sends, player to game payments, pay to continue, and a treasure flow. The game can still run as a guest. Direct send live acceptance is still described as pending in BIS's user stories. | Player to player rewards, tournament entry fees, or quest bounties, with explicit recipient and amount review. |
| 3 | **Balance, history, and live events.** Read spendable/total balances, transaction history, and incoming funds. [Balances](https://docs.arkadeos.com/wallets/operations/checking-balances), [history](https://docs.arkadeos.com/wallets/operations/payment-history) | **Yes.** BIS Account has balance, activity, refresh, and payment/asset observers. | A quest ledger that links a verified payment or reward to the matching game event, while keeping wallet history separate from gameplay state. |
| 4 | **Bitcoin boarding.** Turn confirmed onchain BTC at a boarding address into Arkade funds through batch settlement. [Ramps](https://docs.arkadeos.com/wallets/advanced/ramps) | **Yes, with network and timing constraints.** BIS exposes Bitcoin receiving addresses, automatic onboarding, transfer quotes, status, and settlement recovery. Boarding has confirmation waits and is not an instant deposit. | Show an actionable funding timeline before a paid event starts; avoid admitting an unfunded player until spendable Arkade balance is actually observed. |
| 5 | **Collaborative Bitcoin withdrawal.** Move eligible Arkade funds to a conventional Bitcoin address through the operator's batch process. [Ramps](https://docs.arkadeos.com/wallets/advanced/ramps) | **Yes, with verification limits.** BIS implements Arkade to Bitcoin transfer and reconciliation. Its checkout tracks withdrawal fixes and live acceptance separately. | Let players cash out prizes, with fee, minimum, confirmation, and pending state shown before they commit. |
| 6 | **Bitcoin native assets.** Issue, transfer, reissue where permitted, burn, list, and inspect metadata/supply rules. [Assets overview](https://docs.arkadeos.com/learn/arkade-assets/overview), [SDK asset operations](https://docs.arkadeos.com/wallets/operations/assets/get-started) | **Partly.** BIS demonstrates generic mint, list, deliver, and burn flows, marketplace items, equipment, and level trophies. It does **not** demonstrate the whole asset policy surface, such as a general reissuance workflow or independently verified supply/metadata policy UI. | Limited edition loot with transparent supply, tradable trophies, or crafting that burns inputs and issues a new item. Verify the actual asset rules before promising scarcity. |
| 7 | **Programmable Bitcoin contracts.** Lock spending behind multiple signatures, hashes, deadlines, or refund paths. [Contract examples](https://docs.arkadeos.com/contracts/deep-dive), [escrow](https://docs.arkadeos.com/contracts/escrow) | **Partly.** BIS has a specific limited time treasure offer with claim, reject, expiry, and refund handling. It is not a general contract builder. | Player wager escrow, cooperative boss bounty, or a timed auction, each with explicit timeout and recovery behavior. |
| 8 | **VTXO maintenance and recovery.** Renew expiring virtual outputs, recover eligible positions, and preserve exit data. [VTXO management](https://docs.arkadeos.com/wallets/advanced/vtxo-management) | **Partly.** BIS reads VTXOs and reconciles interrupted sends, boarding, and contracts. Its wallet adapters create temporary SDK wallets; the checkout does not expose a persistent `VtxoManager` renewal service or expiry dashboard. | An account health panel showing spendability, batch expiry, renewal status, and the reason funds are temporarily unavailable. This needs a durable background strategy, not just a game screen. |
| 9 | **Unilateral Bitcoin exit.** Broadcast an eligible pre-signed path without operator cooperation, paying onchain fees and observing timelocks. [Exit process](https://docs.arkadeos.com/wallets/advanced/ramps), [security model](https://docs.arkadeos.com/learn/core-concepts/security-and-trust-model) | **No BIS user workflow found.** BIS's collaborative withdrawal and interrupted-operation recovery are different from an independent `Unroll` exit. Arkade's underlying guarantee should not be presented as a BIS button. | A guided emergency export/exit handoff, with preserved recovery data and an honest cost estimate. Feasibility depends on output state and Bitcoin fees. |
| 10 | **Cross route payments and exchange.** Use quote based Intents for Lightning payments or asset swaps, with route specific fill/refund behavior. [Intents](https://docs.arkadeos.com/intents/overview), [developer preview](https://docs.arkadeos.com/intents/developer-preview) | **No live BIS flow.** BIS's Lightning invoice receive section is explicitly unavailable; its marketplace exchanges game assets through BIS wallet operations, not Arkade Intents. Intents is in developer preview and route availability cannot be inferred from Arkade support alone. | Pay an invoice from a game balance, price an item in another supported asset, or compare provider quotes. Start by verifying a working provider and complete refund/recovery path on BIS's target network. |

## Best opportunities to investigate

1. **Wallet health and recovery** (#8–9): the biggest gap between “funds are visible” and “players understand whether their funds remain recoverable.” Prototype read only status first, then validate renewal and exit on the actual test operator.
2. **Escrow style game mechanics** (#7): BIS already has one timed contract. A reusable contract product could support auctions or wagers, but each path needs a clear claim, cancellation, and timeout design.
3. **External approval for large writes** (#1): useful for a shared game wallet or valuable assets; see [Arkade wallet workflows](arkade-wallet-workflows.md). This is an application security choice, not a requirement imposed by Arkade.
4. **Lightning or asset exchange** (#10): potentially compelling gameplay, but BIS should only expose it after provider availability, fees, failure states, and refund behavior are verified on its target network.

## Local evidence and scope

- Adjacent BIS checkout: `BIS/packages/integration/src/client/wallet-layer-arkade/` implements wallet adapters; `BIS/packages/integration/src/client/state-layer-core/` implements operation state; `BIS/packages/integration/src/client/ui-layer-react/` contains Account review and confirmation screens.
- Adjacent BIS `README.md` and `BIS/documentation/User Story Diagrams.md` distinguish implemented flows from live acceptance and unavailable invoice receiving. `invoice-receiving.ts` returns an unavailable state for Signet.
- This game's [`bis-account.js`](stealth-steel/src/runtime/integration/bis-account.js) and [`bis-host-game.js`](stealth-steel/src/runtime/integration/bis-host-game.js) show how the pinned BIS package is mounted and how confirmed effects reach gameplay. [`BIS_PROVENANCE.md`](stealth-steel/vendor/BIS_PROVENANCE.md) identifies the local package snapshot. Changes in the adjacent BIS source are not automatically changes in that pinned package.
